## Architecture rules
- Event data (sessions, speakers, sponsors) is fetched client-side via src/lib/data.ts: network-first with no-store and a 4s timeout, falling back to a localStorage copy (shown as offline data); the SW also uses NetworkFirst for these URLs. No backend in phase 1.
- Pure event rules (room fallback, overlaps, "now", .ics/Google links) live in src/lib/event.ts with tests in src/lib/event.test.ts; keep them free of React/browser globals.
- All UI strings go through src/locales/{fr,en}.json via useI18n(); never hardcode user-facing text.
- Service worker is generated by vite-plugin-pwa into dist/client and registered only via src/lib/pwa.ts (guards dev/preview/iframes); the manifest is static in public/.
- Likes are device-local (localStorage, src/lib/likes.ts) until accounts exist.
- Floor plan images live in public/plans/ (rdc.svg, etage-1.svg); replace files to update the map.
- Phase 2 uses generated Lovable Cloud clients and TanStack server functions for internal privileged actions; do not create Edge Functions, because this app runs on TanStack Start.
- Account pages live under the client-only `_authenticated` layout with an inline sign-in invitation; private reads and writes use authenticated RLS clients, and privileged operations validate their authority server-side.
- Never cache account pages or private responses in the service worker; only public event pages are eligible for navigation caching.
- Administrative authorization uses protected user_roles rows; profile_status.is_admin is display-only and editable invitation email never grants administrative access.
- Keep networking validation and sorting browser-independent in src/lib/networking.ts, with concrete rule tests alongside it.
- Organizer badges are display-only, sourced from the protected organizer_emails list and synchronized by database triggers at status creation and confirmed email changes; never use them for authorization.
- Email signup/login shares the passwordless flow; the account layout gates incomplete profiles with the two-step onboarding form, and completion is validated by the shared schema and database trigger. LinkedIn prefill uses server-only Airscale with durable per-account reservations and manual fallback.
- Signed-out account screens and /login render the shared EmailSignIn form directly, avoiding a second welcome-to-login step.
- Keep messaging rules browser-independent in src/lib/messaging.ts; private states are returned through authenticated RPCs so declined requests remain hidden from their sender.
- Messaging is in-house (Postgres + Realtime): authenticated users only SELECT via RLS; every write goes through SECURITY DEFINER RPCs (send/edit/delete/react/read/heartbeat) that re-check membership, blocks, suspension, closure and the read-only cutoff, because the database is the only trustworthy enforcement point. Sends go through the sendMessage server function so push follows; database triggers broadcast changes on private `conversation:{id}` topics guarded by realtime.messages policies.
- Browser notifications use a separate worker under /notifications/ and Worker-native Web Push; sender keys remain server-only except the public subscription key.

- Phase 4 modules live in src/lib/phase4: pure schemas/rules have focused tests, provider code stays in server helpers, and authenticated RPCs validate access before privileged work.
- Purge runs in bounded leased batches, checks its dated paused control before destructive stages, preserves two verified designated admins, and is never executed destructively in tests.

- App emails go only through the scaffolded Lovable send helper from src/lib/app-emails.server.ts, each send claimed by a database timestamp first, because this guarantees deduplication and a single provider.
